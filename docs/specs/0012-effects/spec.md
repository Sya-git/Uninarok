## 1. Why

Nothing visual happens in the world beyond units and numbers: a warp portal is an empty cell (SPEC-0009 FR-2, BACKLOG), a level up shows nothing, a Fire Bolt will be damage from nowhere once SPEC-0015 lands. The original client draws all of this from its own data, where effects are files located by path: STR animations (keyframed textured quads, each listing its textures; an STR holds no sound), effect sprites, textured quads, cylinders, models and a few hand-coded procedures. Which parts, sounds and timings make up the effect a skill or the server names by number is a separate mapping (SPEC-0014). The owner has extracted the effect files by hand into our working data (2,996 STR files, 21,757 effect textures, 179 effect tool files). This spec is agnostic of gameplay: it checks that data, imports it, sets the import rules, and makes each imported effect play on its own, by path, so the owner can confirm it visually. The numeric id to effect mapping and which skill shows which effect are SPEC-0014's data, when and where it shows is SPEC-0015's, the warp portal on the map is SPEC-0006's (BACKLOG), game use of the server's effect packets is out of scope, and the sound is SPEC-0013's; all of them need the effects to exist first.

## 2. Goals

1. The client data's effects play as their data describes them: parts, timing, speed and blend from the files, confirmed visually by the owner (preview window, screenshot or in game).
2. One effect catalog keyed by file path, as the client data locates effects: one data asset per effect file holding what the file holds (frame rate, length, layers, keyframes, textures, blends), changeable without code, on which SPEC-0014 builds its effect table by id.
3. Each effect can be checked alone, by path, as a visual test of the importer and player only: an editor preview window (like the sprite preview of SPEC-0007 and the unit composer of SPEC-0009) to browse the catalog and check each imported effect, a dev command in the game, and the warp portal's files as the one real asset verified end to end.
4. Hundreds of effects at once with no per-frame garbage; importer and player tested without a scene; the look confirmed by the owner in the preview window, by screenshot or in game.

## 3. Non-goals

- Placement, attachment, travelling, start delays and lifetime rules for gameplay (on caster, on target, flying to the target, on ground cells, while casting, cancel, pooling and cleanup policy): out of scope; SPEC-0015 decides them for skills. This spec gives only the minimum of FR-6 needed to verify an effect.
- The effect table by numeric id (an id or `EF_*` name to its list of parts: STR path, sprite or procedural function, with each part's wav, start delay, duration, duplicates and attachment), its alias checks, and the data behind it (classic skills' ids in the executable, the client's `effectid.lub`, the skill effect list): SPEC-0014. This spec is addressed by path only and holds no numeric id.
- The skill-to-effect table (roles, per-skill coverage of `NPC_*`, novice, first and second class skills) and the skill-to-motion table: SPEC-0014. Skill moments, skill packets, the skill cursor, the cast bar and the caster's pose: SPEC-0015. Skill effects (cast aura, lock-on, ground-cast marker, per-skill effects) are entries of the effect catalog like any other and are verified playing by SPEC-0014/0015, not here.
- Game use and visual tests of the server effect packets (effects on units in view by id, level up, refine and other typed notices): out of scope here (they need the id table of SPEC-0014; BACKLOG). The warp portal as a world feature (job 45 units showing the warp portal effect; SPEC-0009 FR-2 stays "draws nothing"): SPEC-0006, which the owner will expand (BACKLOG). Here the portal's files are only a test input (FR-7).
- Sound of any kind (effect wavs, positional sound, ACT frame-event sounds, volume): SPEC-0013 Audio. STR files hold no sound reference; which wav goes with an effect part is SPEC-0014's per-part data. Effects play silently here.
- Combat visuals SPEC-0011 left over (hit and critical effects, non-arrow monster projectiles, teleport and logout visuals): out of scope, listed in the BACKLOG.
- Status-change visuals (auras of buffs, hiding, stone, freeze) and status icons: out of scope.
- Map effects: RSW effect emitters (SPEC-0006 FR-9 keeps them as placeholders), weather, map sounds, background music and the warp portal on the map: SPEC-0006, which the owner will expand to include them (revise, not a new spec). Not trivial (many are procedural), left out here; the effect preview window of FR-11 can still play their effect files by path.
- Heal and damage numbers (SPEC-0011, BACKLOG); 3D (Granny) monsters.
- Hat effects (`HAT_EF_*`) and footprint effects (`FOOTPRINT_EF_*`): they use their own id spaces and their own tables, not SPEC-0014's effect table; out of scope.

## 5. Success criteria

- From Bootstrap, in a development build on a local Hercules: `/effect <path> <x> <y> loop` with each warp portal path on a prontera warp's cell shows that part of the portal (FR-7), with no warning, confirmed by the owner in game by screenshot.
- Every must-list entry (FR-5: one per part kind, plus the warp portal's files) plays in the effect preview window (FR-11) with real parts, its inspector shows no missing texture and the owner confirms its look from a saved image; every other catalog entry plays its real parts or a placeholder with one warning; the warning list and the doubtful values are saved with the evidence.
- FR-9: 0 B per frame under its load.
- A release player build contains no dev effect tools (FR-8), and no player build contains the effect preview window (FR-11).
- The FR-1 check report (counts per kind, missing files) is saved with the evidence.
- Evidence is our own captures (images saved from the effect preview window, FR-11, and screenshots from the game), confirmed visually by the owner, plus the offline tests against the client data files; the original client is not run for comparison (owner, 2026-11-24).

## 6. Assumptions and constraints

- No GRF is provided or read. The owner has extracted the effect files by hand into the working data folder (not in the repository): 2,996 STR files, 21,757 effect textures and 179 effect tool files, plus the trap model used as the model entry of the must-list (FR-5). FR-1 only checks and reports what is there. A file still missing plays a placeholder with one warning.
- Effect texture names: where a `.tga` and a `.bmp` of the same name both exist they differ and are two textures; effect textures keep their extension, and a lookup by name alone prefers `.tga` over `.bmp` (FR-2).
- The client data files (STR, effect textures, SPR/ACT, effect tool tables) are the source of values; offline tests compare our imported numbers with those files' contents. Correct look is confirmed visually by the owner (preview window, screenshot, in game), not by running the original client. roBrowserLegacy (GPL v3) is a lead for facts only (which effect, when, how fast, how long): nothing of it is copied; the authored assets of FR-4 are our own data, checked against the client data (effect tool tables, STR headers).
- `PACKETVER` 20220406 (Hercules). No packet is handled in this spec.
- The original client's lub files and tables locate effect files by path (STR files and effect textures under its effect texture folder, effect sprites under its sprite folder; the effect tool tables are per-effect files named by file), so FR-5 keys the catalog by path. Server packets and map emitters carry numeric ids, the skill effect list uses `EF_*` names (mapped to ids by the client's `effectid.lub`) and classic skills use numeric ids hard-coded in the executable: the mapping from those ids to parts, sounds and timing is SPEC-0014's table, not this spec's.
- To verify in the plan against real files: that an STR's textures sit in its own folder or under the effect texture root (FR-2 lookup order), and which effect textures use a pink key and which a black one, and whether the rule follows the texture or the keyframe's blend mode (FR-2, FR-5 keep it as data either way).
- STR effects are drawn by our own small player (STR is keyframed quads with per-keyframe blending, not a particle system). Effects with no STR (quads, cylinders, procedural; e.g. the warp portal's rings and sparkle) are authored data drawn by the same player or a sibling player of the same family, built as the original client builds them per the roBrowserLegacy lead (owner decision 2026-11-24: no visual effect graph, as compute shaders are a risk on mobile); hand-built procedural effects are few and made from what the data and leads describe, their look confirmed visually by the owner. Every effect has a play-speed multiplier (FR-4).
- The project has a Mobile URP asset; the effect player needs no compute shaders, so effects run wherever the rest of the client draws.
- FR-9's cost requirement holds whatever the drawing approach; if one renderer per layer is costly, the plan chooses another way within that requirement.
- Lighting stays real-time (project rule); effects are unlit, blended as their data says.
- Dev-only code is compiled only under `#if UNITY_EDITOR || DEVELOPMENT_BUILD` (project rule).
- No audio code and no wav data here: STR files reference no sound; the wav of an effect part is per-part data of SPEC-0014's effect table (authored, from leads), played through SPEC-0013.
