## 1. Why

To show skills, SPEC-0015 needs to know, for every skill id, what the client data and the known facts say about it: name, icon, target kind, the caster's motion, which effect plays in which role, the cast-bar look and the refusal messages. Part of this is in the client's compiled Lua data (skill lists per language, the newer skills' effect list, actor states, delays, message table). The rest (classic skills' motions and effects) lives only in the client executable, so it has to be written by us from facts (the reference note [original-client-skill-data.md](original-client-skill-data.md)) and kept editable. The owner split skills in two (2026-11-24): this spec **imports and authors the data**, offline; SPEC-0015 **replicates the behaviour** at run time from it. The skill-to-effect table, first planned in SPEC-0012, is built here, and so is the effect table by id it rests on: classic skills (in the executable), the server's effect packets and the client's skill effect list (by `EF_*` name, resolved through the client's `effectid.lub`) all name an effect by a numeric id, while SPEC-0012 imports and plays effect files by path only. The table says, for each id, which parts (STR, sprite, procedural) play, with which sound and timing; STR files hold no sound, and the original client keeps these links in its executable, so they are authored by us from facts.

## 2. Goals

1. The client's skill-related Lua data decoded offline into our own data, with a report of what was and was not decoded.
2. One skill catalog, one motion table, one effect table by id, one skill-to-effect table, one refusal-message table and one set of client constants, all data, editable without code, each entry marked by source (client data, server, lead).
3. Coverage and consistency checked offline and saved as evidence; values confirmed by the owner in the editor table viewer and, through SPEC-0015, in game, not by comparison with the original client.

## 3. Non-goals

- Anything at run time: the skill list from the server, choosing and casting, cursor, cast bar drawing, walk lock, results, the moments effects start (SPEC-0015).
- Drawing effects, the effect catalog (one asset per effect path), STR import (SPEC-0012). This spec's effect parts only reference SPEC-0012 assets by path.
- Sound playback (SPEC-0013 Audio); wav names are kept here only as per-part data of the effect table (FR-4).
- Playing an effect by id at run time (SPEC-0015 for skills). Game use of the server's effect packets (effect on a unit by id, level up, refine), and a packet-driven visual test of them: out of scope (BACKLOG).
- Hat (`HAT_EF_*`) and footprint (`FOOTPRINT_EF_*`) effects, with their own id spaces.
- Skill icons' import (SPEC-0008 FR-7; the catalog only links to them by skill id); skill descriptions and the skill tree window; homunculus, mercenary and pet skills beyond what the client files list.
- Network and scenes: nothing here talks to a server or needs a scene.

## 5. Success criteria

- The decode report and the FR-8 listing are saved as evidence, with 0 skills lacking an effect row or "no effect" entry among `NPC_*`, novice, first- and second-class skills, and the lead rows still to check counted.
- The SPEC-0015 success-criteria skills (Bash, Magnum Break, Fire Bolt, Fire Wall, Double Strafe, Heal, Increase AGI, Endure) and the acolyte warp portal unit have full catalog, motion and effect rows, and every effect id they use has an FR-4 row whose part paths all have SPEC-0012 assets.
- The FR-9 tests pass; the owner has reviewed those rows in the editor table viewer; nothing is compared with the original client running.

## 6. Assumptions and constraints

- Depends on SPEC-0002 (importer family, game data), SPEC-0008 (skill icons, lub reading), SPEC-0009 (unit actions), SPEC-0012 (effect assets by path). Used by SPEC-0015 (consumes the effect table by id and the skill tables) and SPEC-0013 (plays the parts' wav names).
- Client data: the LATAM client's lub files, extracted by hand by the owner into the working game data (no GRF is provided or read); they are the source of values, and offline tests compare decoded values with those files' contents; classic skills' motions and effects are not in any data file (they are in the executable), so their rows rest on leads and stay editable.
- Hercules' skill db (renewal) is the server reference; at run time the server's packets rule (SPEC-0015).
- `PACKETVER` 20220406 matters only for which skill ids and refusal causes exist; no packet is touched here.
- roBrowserLegacy is a lead for facts only; nothing is copied. Its effect table (numeric id to parts) shows which parts an id has; its wav names and timings are roBrowser's own authoring, not read from STR files, so ours are marked "to check".
